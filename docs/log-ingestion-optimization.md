# Log Ingestion 개선 계획 및 구현

2026-10-08. 구현·운영 배포 완료. Supabase DB 설정 변경은 하지 않았다.

## 근거와 한계

- 운영 대상: `mvngtkoqjejvwygikvhi` (싱가포르), 배포 앱 `4c043e1`.
- 9/8~10/8 Log Ingestion 1.367GB. 최근 24시간 API Gateway 13,785건 중 재수강 대기 조회 9,255건, 예약 공지 1,238건, 결제 만료 1,236건.
- 후속 24시간 조회에서 Warp timeout 문구 포함 PostgREST 로그 994건, 본문 56,303문자. 조회 시간이 이동하므로 앞선 집계와 전체 건수가 조금 다르다.
- 건수/본문 문자 길이는 메타데이터 포함 수집 바이트가 아니다. 월간 초과의 원인을 확정하거나 감축률을 보장하지 않는다.
- PostgREST 공식 이슈 https://github.com/PostgREST/postgrest/issues/4799 는 정상 동작 중 동일 문구가 기록되는 문제와 수정을 설명한다. 이 프로젝트에 해당하는지는 서비스 버전 확인이 필요하다.

## 1단계: 기능을 보존한 요청 감축 (이번 구현)

수강별 대기 조회를 100개 부모 ID 단위의 일괄 존재 조회로 전환한다. `id,renewed_from_enrollment_id`만 받고 ID 기반 100행 페이지 조회로 API 행 제한과 중복 대기 행에 따른 누락을 방지한다. 후보가 없으면 DB 요청도 없다.

실제 대기 건이 있는 부모만 기존 전체 조회/중복 정리를 수행한다. 기간이 지난 부모도 대기 건이 있으면 기존 중복 정리를 유지한다. 신규 생성은 기존 `confirmRenewalEnrollmentInDb`의 DB 재확인·정책·슬롯 검증을 그대로 거친다. 일괄 조회가 실패하면 빈 결과로 처리하지 않고 작업을 실패시킨다. 존재 조회는 권한 검증이나 트랜잭션 잠금을 대체하지 않는다.

스케줄러의 1분 주기, 학생 신청 12시간/대기 15시간 정책, 예약 공지 발송, 결제 만료, 기존 로컬의 수업 변경 만료 작업, API 응답·인증은 변경하지 않는다. 장기적인 음성 캐시는 도입하지 않는다.

최근 관측한 대기 없는 후보 8개 상황에서 재수강 확인 요청은 분당 8회→1회(87.5% 감소)다. 대기 건이 실제 존재하면 기존 정리를 위한 조회가 추가된다. 전체 로그 바이트 절감률은 배포 후 측정해야 한다.

## 2단계: Warp 로그 원인 확인 (운영 후속)

1. Supabase의 운영 PostgREST 버전과 공식 수정 포함 여부 확인.
2. 같은 UTC 구간의 Warp 로그, API 지연/504, `PGRST003`, DB pool 대기, CPU/메모리, 연결 재생성 기록을 대조.
3. 실제 요청 실패면 느린 쿼리·잠금·pool 병목부터 해결. 오해를 부르는 로그만 발생하면 Supabase 지원을 통해 관리형 서비스 패치 적용 경로 확인.
4. 근거 없이 로그를 끄거나 타임아웃·pool 크기를 늘리거나 서비스를 재시작하지 않는다.

## 검증 및 배포 기준

- `npm run test:renewal-maintenance`: 실제 조회 헬퍼와 repository 제어 흐름을 격리 실행. 빈 후보, 8→1 요청, 100행 초과 중복, ID 분할, 조회 실패, 미래 수업, 만료 중복 정리, 기존 대기 재사용, 생성 경로, 다른 대기 수강 차단 검사. 운영 DB에 쓰지 않는다.
- 타입 검사, production build, 인증/초기화/수업변경 경계 검사.
- 기존 `test:transactions`는 실제 DB 데이터 생성·삭제를 수행하므로 운영 DB 대상으로 자동 실행하지 않는다. 격리 DB에서 후속 실행한다.
- `4c043e1`로 운영 배포 완료. 기존 migration 053·054와 재수강 유지보수 최적화 변경을 같은 릴리스에 포함했다.
- 배포 후 동일 UTC 구간에서 API별 건수, 4xx/5xx, Warp 로그와 처리 지연을 비교하고 48~72시간 일일 수집량 확인. 예약 발송/결제 만료/재수강 생성이 누락되면 기존 릴리스로 롤백한다.
