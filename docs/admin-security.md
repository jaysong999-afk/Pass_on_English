# 관리자 페이지 보안 운영 가이드

## 적용된 구조

- 관리자는 개인별 계정을 사용하고 TOTP 인증 앱으로 2단계 인증을 등록한다.
- TOTP는 Supabase 프로젝트에서 기본 활성화되고 무료로 제공된다. 별도로 SMS 공급자를 계약하지 않는다.
- `ADMIN_MFA_MODE=optional`에서는 등록과 검증을 준비하되 기존 관리자 접근을 막지 않는다.
- 두 관리자의 등록과 재로그인 확인 후 `ADMIN_MFA_MODE=required`로 바꾸면 관리자 페이지와 관리자 전용 API가 모두 AAL2 세션만 허용한다.
- 관리자 변경 API는 동일 출처의 브라우저 요청 또는 명시적 Bearer 인증만 허용한다.
- 잘못된 로그인은 브라우저가 보내는 역할 값과 무관하게 앱 프로세스 메모리에서 이메일+IP 및 IP 단위로 제한한다. 공격자가 역할 값을 바꿔 관리자 계정 보호를 우회할 수 없고, Supabase에 실패 로그를 매번 쓰지 않아 공격 시 DB 트래픽도 증가하지 않는다.
- 로그인 성공, MFA 등록·검증, 비밀번호 변경, 다른 기기 로그아웃은 `admin_security_events`에 최소 정보만 기록한다. 원본 IP는 저장하지 않고 HMAC 해시만 저장한다.
- 비밀번호 변경은 현재 비밀번호를 다시 확인하며 14자 이상·문자군 3종류 이상을 요구한다. 성공 시 현재 기기를 제외한 기존 세션을 종료한다.
- MFA 확인 시점은 위조 방지 서명된 HttpOnly 쿠키로 7일 동안만 인정한다. 기간이 지나면 유효한 로그인 세션이라도 인증 앱 번호를 다시 확인한다.
- TOTP 번호 생성은 인터넷이나 VPN에 의존하지 않는다. 중국에서 VPN 출구 IP가 바뀌어도 별도 IP 허용목록 때문에 차단되지 않는다.

## 운영 활성화 순서

### 1. DB migration 적용 (완료)

운영 Supabase가 반드시 싱가포르 프로젝트 `mvngtkoqjejvwygikvhi`인지 확인한 뒤
`supabase/migrations/057_admin_security_audit.sql` 파일만 단독 트랜잭션으로 적용한다.
이 프로젝트는 migration 이력 테이블이 없으므로 `supabase db push`나 과거 migration 전체 재실행을 사용하지 않는다.

적용 후 다음을 확인한다.

- `public.admin_security_events` 테이블과 인덱스 2개가 존재한다.
- RLS가 활성화되어 있다.
- `anon`은 접근할 수 없다.
- `authenticated`는 SELECT 권한만 갖고 관리자 RLS를 통과해야 조회할 수 있다.
- `service_role`은 감사 이벤트를 기록할 수 있다.

2026-10-19 싱가포르 운영 프로젝트에 migration 057만 단독 적용했다. 위 항목을 모두 검증했으며, `anon` 실제 REST 조회는 `401/42501`로 거부됐다. 역할별 실제 조회·기록 시험에 사용한 임시 감사 행은 검증 직후 제거했다.

### 2. 운영 비밀값 준비

Windows PowerShell에서 아래 명령으로 감사 로그 IP 해시용 비밀값을 1회 생성한다.

```powershell
$securityBytes = New-Object byte[] 48
[Security.Cryptography.RandomNumberGenerator]::Fill($securityBytes)
[Convert]::ToBase64String($securityBytes)
```

표시된 값은 비밀번호 관리자에 보관하고 Git, 문서, 채팅에 붙여 넣지 않는다.

### 3. Tencent 운영 환경을 준비 모드로 시작

현재 릴리스의 `deploy/tencent-lighthouse/.env.production`에 아래 항목을 추가한다.

```dotenv
ADMIN_MFA_MODE=optional
ADMIN_SECURITY_EVENT_HMAC_KEY=<2단계에서 생성한 값>
ADMIN_MFA_SESSION_SECRET=<2단계에서 별도로 한 번 더 생성한 값>
ADMIN_MFA_MAX_AGE_DAYS=7
```

환경파일 권한은 기존과 같이 소유자만 읽을 수 있는 상태를 유지한다. 앱 배포 후 값이 컨테이너에 주입됐는지만 확인하고 원문은 출력하지 않는다.

### 4. 두 관리자 모두 MFA 등록

각 관리자가 자신의 계정과 휴대전화로 따로 진행한다.

1. 관리자 페이지에 로그인한다.
2. 왼쪽 메뉴의 `로그인 보안`을 연다.
3. 휴대전화에 2FAS, Google Authenticator 또는 Microsoft Authenticator 중 하나를 설치한다.
4. `인증 앱 등록 시작`을 누르고 QR 코드를 스캔한다.
5. 인증 앱에 표시된 6자리 번호를 입력해 등록을 완료한다.
6. 관리자 페이지에서 로그아웃한 뒤 다시 로그인하고, 6자리 번호 입력이 정상 동작하는지 확인한다.
7. `다른 기기에서 로그아웃` 기능도 각 계정에서 1회 확인한다.

QR 코드와 수동 입력용 비밀키는 메신저로 공유하거나 화면 캡처로 보관하지 않는다. 두 관리자는 하나의 MFA 항목을 공유하지 않고 각자 계정에 각자 등록한다.

### 5. 의무화 전 최종 확인

- 두 관리자 모두 서로 다른 관리자 계정으로 로그인할 수 있다.
- 두 계정 모두 `로그인 보안` 화면에서 `인증 완료`가 표시된다.
- 각 계정에서 로그아웃→이메일/비밀번호 로그인→6자리 인증→대시보드 진입이 성공한다.
- 한 관리자의 휴대전화 분실 시 다른 관리자가 운영을 계속할 수 있다.
- 비밀번호 관리자에 두 계정의 복구 절차와 담당자가 기록되어 있다.

### 6. MFA 의무화

운영 환경값을 다음과 같이 바꾼다.

```dotenv
ADMIN_MFA_MODE=required
```

앱 컨테이너를 안전하게 재생성하여 환경값을 다시 읽게 한다. 변경 후 일반 관리자 화면과 관리자 API가 AAL1 세션을 거부하고 `/admin/security`로 안내하는지 확인한다. 문제가 있으면 즉시 `optional`로 되돌리고 컨테이너를 재생성하면 비밀번호 로그인으로 복구할 수 있다.

## 운영 주의사항

- 관리자 계정이나 비밀번호를 공동 사용하지 않는다.
- 휴대전화 교체 전 새 인증 앱 등록·검증을 먼저 완료한다.
- 관리자 이메일 계정 자체에도 2단계 인증을 켠다.
- 정기적인 비밀번호 강제 교체는 하지 않되, 유출 의심·담당자 변경·공용 사용 발견 시 즉시 변경한다.
- CSP는 초기 배포에서 `Report-Only`로 관찰한다. 정상 리소스 차단 위험이 없음을 확인한 뒤 별도 변경으로 강제 정책 전환을 검토한다.
- 실패 로그인 제한은 앱 메모리와 Nginx의 이중 방어다. 현재 단일 앱 인스턴스에는 적합하며, 다중 인스턴스로 확장할 때 공유 저장소 기반 제한으로 교체한다.
